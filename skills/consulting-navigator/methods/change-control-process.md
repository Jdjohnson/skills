# Change Control Process
## Purpose
Govern mid-project scope, cost, and schedule changes through a formal request-impact-approve cycle so the baseline stays intentional. It turns requests into traceable decisions and updates the plan only when authorized.
## Use
- A baselined project must absorb scope, cost, or schedule change requests without losing control
- Sponsors need an auditable approve/reject path for mid-flight changes
- Multiple workstreams generate conflicting change requests that need triage
## Avoid
- You are still defining the initial baseline—use waterfall-methodology or pmbok-framework first
- The work is intentionally adaptive discovery with no fixed baseline—use scrum-framework
- You need enterprise portfolio risk, not project-level change decisions—use enterprise-risk-management
## Inputs
**Must-have:**

- Approved project baseline (scope, schedule, cost, quality)
- Documented change requests with impact estimates
- Decision authority matrix (who can approve at each threshold)
- Current risk and issue registers
- Budget and contingency remaining

**Nice-to-have:** contract change clauses, benefits case, configuration records, dependency schedule, and vendor quotations.

**When data is thin:** log the request, appoint an analyst, and defer the decision rather than allowing verbal approval to become unrecorded work.
## Procedure
1. **Capture and classify the request.** Assign a unique identifier, requester, reason, affected baseline element, urgency, and links to risks, defects, or contract obligations. Reject incomplete requests back to the owner. Output: change register entry.
2. **Triage against authority thresholds.** Decide whether the request is a correction within delegated tolerance, requires detailed analysis, or must go to the sponsor or control board. Protect urgent safety or regulatory action with an expedited, still-recorded path. Output: routing decision.
3. **Assess integrated impact.** Estimate the scope, schedule, cost, quality, resource, risk, benefit, procurement, and dependency effects; identify displaced work and contingency consumption. Compare alternatives including reject and defer. Output: impact statement and recommendation.
4. **Decide and communicate.** Present the request with a recommendation to the authorized person or board. Record approve, reject, defer, or request-more-information along with conditions and rationale. Output: dated decision log.
5. **Rebaseline and verify implementation.** Update controlled scope, schedule, budget, contract, and configuration documents only after approval. Track the approved change to completion and confirm its actual impact. Output: revised baseline and closed change record.
## Output Contract
The process produces a change register and decision pack containing the request, baseline affected, complete impact analysis, alternatives, authority route, decision, conditions, updated baseline references, and implementation status. It can answer what changed after kickoff, who authorized it, and which approved changes consumed contingency.
## Evidence
Use baseline versions, estimates from accountable workstream leads, contracts, and risk-register entries as observed evidence. Tag preliminary vendor prices, resource availability, and benefit effects as assumptions. Preserve the original request even if it is revised. A change cannot be marked approved solely because work has begun; emergency work requires retrospective authorization and visible exception status.
## Checks
- Every request has a unique ID, owner, date, and baseline reference.
- Impact analysis covers cross-workstream consequences, not only the requester's task.
- Approval authority matches the cost, schedule, and scope threshold.
- Rejected and deferred requests remain visible in the register.
- Approved changes update all affected controlled documents once, with version traceability.
## Failure Modes
- Calling a scope addition a “clarification” to bypass the board.
- Approving schedule relief without pricing its supplier or benefit impact.
- Letting a vendor start extra work before the authority decision.
- Rebaselining to hide a variance rather than recording the approved change.
- Closing the request at approval and never checking whether implementation matched the decision.
