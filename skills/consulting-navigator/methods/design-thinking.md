# Design Thinking
## Purpose
Move from user empathy through problem framing, ideation, and low-fidelity prototyping to tested human-centered solution concepts. Replace opinion-led feature or process bets with iterative desirability learning before committing to a build path, holding feasibility and viability in view.
## Use
- The problem is ambiguous and teams start from a preferred solution, not observed user need.
- Requirements are detailed but the users' lived problem is still fuzzy.
- You need low-fidelity desirability tests before investing in build or process redesign.
- Innovation is stuck in brainstorms that never touch real user pain.
- Qualitative insight must shape product, service, or experience design.
## Avoid
- You need business-model validation through ship–measure–pivot economics—use lean startup.
- You need a fixed five-day recipe to a tested prototype—use design sprints.
- The scope is end-to-end service systems (frontstage and backstage)—use service-design-thinking.
- The problem is pure operational throughput with no user experience dimension—use theory of constraints.
- Users cannot be observed or interviewed and no journey evidence exists; gather access first.
## Inputs
**Must-have:** target user group and context of use; access for observation, interviews, or journey evidence; constraints on scope, feasibility, and success criteria; willingness to prototype and test before final design.
**Nice-to-have:** support tickets, usage analytics, competitor experience samples, regulatory limits, brand principles.
With limited field access, use secondary evidence and proxy users, labeling gaps as assumptions to test.
## Procedure
1. **Frame the question.** Name the user group, situation, and open question—not a pre-chosen solution. Output: framing brief and constraints.
2. **Empathize.** Observe and interview users in context; capture jobs, pains, workarounds, and emotions. Output: empathy notes and raw need signals.
3. **Define.** Synthesize findings into a focused, evidence-grounded problem statement and success criteria. Output: point-of-view or how-might-we problem definition.
4. **Ideate.** Generate many solution directions against the defined problem; diverge before converging. Output: concept shortlist tied to the definition.
5. **Prototype.** Build the cheapest representation that can teach—sketch, mock, role-play, paper flow. Output: testable prototype artifacts.
6. **Test and refine.** Put prototypes in front of users; learn what fails; iterate definition, concepts, or fidelity. Output: tested concept package with learning log.
## Output Contract
A package containing: (1) user-grounded problem definition, (2) key empathy insights, (3) concepts considered, (4) prototypes used, (5) test results and revisions, and (6) a recommended concept direction with open desirability, feasibility, and viability risks. It must support a go / iterate / kill decision before roadmap commitment or heavy build.
## Evidence
Separate observed user behavior and quotes (facts) from team interpretations (inferences) and untested beliefs (assumptions); log unknowns. A polished requirement is not evidence of need. When evidence is thin, run another empathy or test cycle rather than debating opinions. Disconfirming tests override stakeholder preference unless a documented constraint forces otherwise.
## Checks
- Problem definition cites user evidence, not only internal goals.
- Ideas not tied to the defined problem are parked.
- Prototypes exist to learn, not to sell a pre-chosen answer.
- At least one documented test cycle with real or representative users.
- Feasibility and viability appear alongside desirability, not as afterthoughts.
- Next build steps are justified by test learning, not workshop enthusiasm.
## Failure Modes
- Skipping empathy and ideating from conference-room opinions.
- Sticky-note volume without a sharp problem definition.
- Over-fidelity prototypes that freeze commitment before learning.
- Confusing the method with a lean-startup backlog or a fixed sprint recipe.
- Workshop loops that never test against users.
- Claiming validation when only internal stakeholders reviewed the concept.
